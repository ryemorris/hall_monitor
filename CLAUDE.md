## Project Overview

Hall Monitor is an automated workflow tool that monitors Quay.io repositories for stale services and updates Tekton SC pipeline configurations. It operates in three phases:
1. Check Quay repositories for services without recent container images
2. Update Tekton SC files in those stale service repositories to use the `main` branch
3. Trigger component builds for unremedied stale services (optional)

## Common Commands

```bash
# Full workflow (check + update + trigger builds)
python -m main.coordinator

# Dry run mode (preview changes)
python -m main.coordinator --dry-run

# Check only (skip updates and build triggers)
python -m main.coordinator --check-only

# Skip build triggering (Steps 1 and 2 only)
python -m main.coordinator --skip-build-trigger

# Process specific services
python -m main.coordinator --services service1 service2

# Individual tools (can run standalone)
python -m main.utils.quay_image_checker --config repos.json --quick
python -m main.utils.update_tekton_sc /path/to/repos --dry-run
python -m main.utils.trigger_component_builds --repos-config repos.json --services service1
python -m main.utils.parse_repos --markdown /path/to/markdown --output repos.json
```

## Architecture

### Three-Module Design

**coordinator.py** - Main orchestrator
- Loads `config.yaml` and `repos.json`
- Calls quay_image_checker to identify stale services
- Maps service names to git repo names (handles special cases like notifications)
- Calls update_tekton_sc to fix stale repos
- Services can share repositories (e.g., all notifications-* services live in notifications-backend)

**quay_image_checker.py** - Quay monitoring
- Uses Quay.io public API to fetch repository tags
- Searches for images matching pattern: `sc-{YYYYMMDD}-{sha}` within date range
- Returns two lists: services with recent images, services without (stale)
- Operates in "report mode" when called by coordinator

**update_tekton_sc.py** - Tekton pipeline updater
- Uses `TektonUpdater` class to manage git operations
- Checks out `security-compliance` branch (or configured branch)
- Finds `.tekton/*-sc*.yaml` files
- Updates pipeline URLs: replaces version tags with `main` branch
- Pattern: `https://github.com/{org}/{repo}/raw/v{version}/{path}` → `https://github.com/{org}/{repo}/raw/main/{path}`
- Commits and pushes to `upstream` remote
- Tracks repos with no changes (important for identifying why services remain stale)

### Key Data Flow

1. `repos.json` maps service names to Quay repository URLs
2. Coordinator checks Quay for images from last N days (default: 14)
3. Stale services are identified (no recent `sc-{date}-{sha}` images)
4. Service names are mapped to git repo names (see `map_service_to_repo()`)
5. Git repos are checked out, SC files updated, committed, and pushed
6. Report shows which services remain stale after updates

## Important Patterns

### Service-to-Repo Mapping
Some services share git repositories. Check `coordinator.py:map_service_to_repo()` for mappings:
- notifications-aggregator → notifications-backend
- notifications-connector-email → notifications-backend
- notifications-engine-sc → notifications-backend
- notifications-recipients-resolver → notifications-backend

When adding new shared-repo mappings, update this function.

### Image Tag Format
The system searches for Quay images with this exact pattern:
- Format: `sc-{YYYYMMDD}-{7-char-sha}`
- Example: `sc-20260208-abc1234`
- The date component is used for filtering recent images

### Git Remote Configuration
All repositories must have an `upstream` remote configured. The updater:
- Fetches from `upstream`
- Checks out from `upstream/{branch}`
- Pushes to `upstream/{branch}`

### Stale Services with No Changes
When a stale service is processed but no files are updated, it's tracked separately. This happens when:
- Branch doesn't exist on remote
- No `-sc` files found in `.tekton` directory
- SC files already use `main` branch (most common)

These cases require investigation beyond automated updates.

## Configuration Files

**config.yaml** - Main configuration
- `repos_config`: Path to repos.json
- `git_repos_dir`: Local directory containing cloned repositories
- `branch`: Git branch to update (default: security-compliance)
- `quick_search_days`: Lookback period for recent images (default: 14)
- `services`: Optional filter for specific services
- `dry_run`: Preview mode toggle
- `markdown_path`: Input for parse_repos.py utility

**repos.json** - Service to Quay repository mappings
- Format: `{"service-name": "quay.io/namespace/path/to/repo"}`
- Generated by `parse_repos.py` from Konflux service references markdown
- Can be hand-edited for manual corrections

## Testing Approach

When making changes:
1. Always test with `--dry-run` first
2. Use `--check-only` to validate Quay checking without git operations
3. Test with `--services` to limit scope during development
4. Check both success cases and edge cases (missing branch, no SC files, etc.)
